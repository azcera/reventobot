# Аудит Revento и план исправлений

Дата: 19 ноября 2026 года. Область: Discord-бот, Express API, PostgreSQL,
фоновые задачи, Telegram/Majestic, React-дашборд, общие модули и проверки.

## Вывод

Основные источники нестабильности — несогласованность БД и внешних действий,
неполное управление жизненным циклом, повторные полные сетевые обходы и
несогласованные черновики/версии в интерфейсе. Ускорение нужно начинать с этих
механизмов. Разбиение файлов само по себе не ускоряет Node.js.

Ниже 35 задач: подтверждённые дефекты, расходы с доказанным механизмом,
ограничения масштабирования и пробелы проверки. Они различаются явно.
P1 — безопасность, потеря данных или серьёзный отказ; P2 — надёжность и
отзывчивость; P3 — объёмозависимая оптимизация и сопровождение.
Приоритет является инженерной оценкой, а не оценкой CVSS.

Это аудит исходников с проверками на локальных фикстурах, а не утверждение,
что исследованы все возможные состояния production. Рабочие Discord/Telegram,
БД и секретные файлы намеренно не использовались для проверки. Реальные p95,
планы SQL, настройки reverse proxy, резервное копирование и нагрузка сервера
не измерены. Внешние действия тестировались с заглушками.

Уже работающие защиты следует сохранить: OAuth state одноразовый, CSRF и
ограничение API настроенным guild присутствуют, сессии хранят хеши токенов,
редактор проверяет владение сообщением, регистрации используют транзакции и
очередь refresh, многие workers уже имеют защиту от наложения запусков.
Явный HTTP auth bypass или XSS в проверенных путях Markdown не подтверждён.

## Безопасность и жизненный цикл

### 01. P1 — уязвимые зависимости

- Доказательство: `npm audit` и `npm audit --omit=dev` находят одинаковые
  4 пакета: 2 high, 2 moderate. `npm ls` подтверждает `body-parser@2.3.0`
  через Express, `undici@6.28.1` через discord.js, `ip-address@10.7.0` через
  teleproto/socks, `qs@6.16.0` через Express/body-parser.
- `express.json` в `index.ts:85` подключён до аутентификации и допускает
  распаковку сжатого тела. Поэтому advisory body-parser относится к доступной
  неавторизованному клиенту поверхности. Для остальных advisory наличие
  пакета доказано, но достижимость каждого уязвимого метода не установлена.
- Исправление: обновить lockfile через совместимые обновления; для body-parser
  использовать исправленную версию от 2.4.0, для ветки undici 6 — от 6.29.1.
  Для qs/ip-address взять исправленные версии из актуального audit и проверить
  совместимость родителей. Не выполнять слепой `npm audit fix --force`.
  Если сжатые JSON-запросы продукту не нужны, отключить inflate как дополнительное
  ограничение поверхности. Встроенный fetch Node проверять отдельно от npm undici.
- Приёмка: чистая установка, сборка, тесты, повторный audit; негативный тест
  сжатого запроса на локальном HTTP-сервере. Версии Node и менеджера пакетов
  зафиксировать для воспроизводимости.
- Первичные источники: [body-parser advisory](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828),
  [undici advisory](https://github.com/nodejs/undici/security/advisories/GHSA-2m5v-pch6-74hx).

### 02. P1 — отключена проверка сертификата PostgreSQL

- Место: `src/services/database.ts:10`, `rejectUnauthorized: false`.
- Следствие: TLS шифрует соединение, но не подтверждает подлинность сервера БД;
  при подмене сетевого узла возможен доступ к данным/учётным данным.
- Исправление: доверенный CA и проверка сертификата/имени сервера. Для локальной
  БД отдельно задавать явную конфигурацию TLS; не переносить небезопасный режим
  на production. Проверить влияние SSL-параметров connection string.
- Приёмка: корректный сертификат принимается; чужой CA и неверный hostname
  отклоняются. Предварительно подготовить CA хостинга, чтобы не оборвать доступ.

### 03. P1 — устаревшая форма отказа может удалить актуальную заявку

- Место: `src/features/invite/inviteModalHandler.ts:14–83`, вызов из
  `src/events/interactionCreate.ts:224`.
- Submit не повторяет проверку `isApplicationMod`, не сверяет channel ID;
  DELETE ограничен user ID. Отзыв роли после открытия окна не предотвращает
  отказ; старое окно может затронуть новую заявку того же пользователя.
- Исправление: актуальные права при submit; идентификатор/версия заявки,
  сервер, канал и ожидаемый статус; единое атомарное состояние accept/reject.
  Изменение через conditional UPDATE/DELETE с проверкой affected rows.
  Внешнее удаление канала выполнять как восстанавливаемый шаг операции.
- Приёмка: отзыв роли, заменённая заявка, чужой канал, параллельный accept/reject,
  ошибка БД; успешный ответ только после подтверждённого изменения состояния.

### 04. P1 — архивные списки изменяют посторонние сообщения бота

- Место: `src/features/archive/updateLists.ts:74–97`.
- Все сообщения текущего бота, кроме membership, считаются страницами списков:
  первые перезаписываются, лишние удаляются. Другая публикация того же бота в
  настроенном канале может быть уничтожена.
- Исправление: реестр управляемых message IDs и типов страниц в БД. При миграции
  распознавать старые списки строго; неоднозначные сообщения оставлять человеку.
  Не считать совпадение author ID доказательством владения конкретной функцией.
- Приёмка: человеческие сообщения, membership и другие публикации этого бота
  сохраняются; редактируются/удаляются только зарегистрированные страницы.

### 05. P2 — запрет массовых упоминаний обходится при новой публикации

- Место: `src/services/containerMessageService.ts:98`, вызов `index.ts:148`,
  описание настройки `src/dashboard/store.ts:51`.
- При `allowMentions=false` остаётся `parse: ['roles','everyone']`, поэтому
  выключенная настройка не блокирует everyone/here при send.
- Исправление: разделить политику send/edit. Для send при false убрать everyone;
  доступные роли/пользователи должны соответствовать явно описанной настройке.
  Существующий контракт edit, закреплённый `tests/messageMentions.test.ts:25`,
  менять отдельным осознанным решением.
- Приёмка: матрица send/edit × true/false, включая everyone/here и роль.

### 06. P1 — запуск продолжается после ошибки инициализации

- Место: `src/services/database.ts:25–83`, `index.ts:25–27,193–198`.
- `initDb()` запускается без await и проглатывает ошибку. Ошибка dashboard.init
  тоже превращается в успешный resolved promise. Через фиксированные 5 секунд
  Discord входит и запускает обработчики с отсутствующими таблицами/настройками.
  HTTP middleware блокирует API при store.ready=false, но не все фоновые задачи.
- Исправление: явный bootstrap: validate env → connect → migrations → load store
  → register handlers → login/start services. Обязательные зависимости должны
  завершиться успешно; transient-сбои — ограниченные retry с backoff, затем exit
  с ненулевым кодом. Задержку 5 секунд заменить зависимостями готовности.
- Приёмка: искусственная ошибка DDL/загрузки настроек не запускает Discord и
  workers; readiness возвращает 503. После успешной инициализации — ready.

### 07. P1/P2 — остановка неполная и может зависнуть

- Место: `index.ts:171–189`, `src/events/ready.ts:21`,
  `src/services/captureExpiry.ts:61–68`, таймер очистки `store.ts:178`.
- CaptureExpiry не хранится в реестре сервисов и не имеет stop; нет pool.end,
  общей границы ожидания и защиты от повторного сигнала. Один rejected stop
  прерывает последующие шаги; сервер продолжает принимать запросы до конца
  остановки workers; flush ошибок может ждать большую очередь.
- Исправление: единый идемпотентный lifecycle registry. Сразу снять readiness и
  прекратить новые операции; закрыть HTTP listener, остановить producers,
  дождаться/отменить активные задачи с deadline, закрыть Discord и pool.
  Ошибки остановки собирать без пропуска остальных ресурсов. По deadline —
  принудительное завершение с диагностикой, состояние операций сохранять заранее.
- Приёмка: двойной SIGTERM, зависший stop/HTTP/Telegram и ошибка одного сервиса;
  завершение ограничено по времени, новые записи не принимаются.

### 08. P1 — продолжение работы после uncaughtException

- Место: `index.ts:209–211`; обработчик только логирует исключение.
- Состояние процесса после необработанного исключения может быть повреждено.
  Нормальное обслуживание запросов после него не даёт гарантии корректности.
- Исправление: минимальная аварийная диагностика и завершение с ненулевым кодом;
  внешний supervisor перезапускает процесс. Восстановление работы — через
  сохранённые операции и reconciliation. Обычные ошибки перехватывать локально.
- Приёмка: дочерний тестовый процесс падает ожидаемым кодом и не продолжает
  обслуживание. Политику unhandledRejection определить отдельно.
- Источник: [рекомендации Node.js](https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly).

## Согласованность операций и Discord

### 09. P1 — гонка и незавершённое создание заявки

- Место: `src/features/invite/inviteApplication.ts:148,184,191,214`.
- Между SELECT существования и INSERT создаётся канал. Два submit создадут два
  канала; проигравший INSERT оставит лишний. Ошибка send после INSERT оставляет
  заявку без сообщения/кнопок и блокирует новую.
- Исправление: durable claim по пользователю, состояние creating/pending/failed,
  channel/message IDs, повторяемые шаги восстановления. Уникальный claim должен
  предшествовать созданию канала; при неоднозначном сетевом результате сначала
  искать результат операции, затем решать о повторе или компенсации.
- Приёмка: два одновременных submit и падение после каждого шага; после рестарта
  одна рабочая заявка либо понятное failed-состояние без бесхозного канала.

### 10. P1/P2 — объявление сбора отправляется до сохранения регистрации

- Место: `src/features/capture/captureManager.ts:336–352`.
- При успешном send и неуспешном INSERT публичные кнопки не имеют записи в БД.
- Исправление: запись операции до send, operation ID, состояние отправки,
  привязка message ID и recovery. При известном отказе — компенсация; при
  неопределённом исходе — сверка результата. Exactly-once между Discord и БД
  одной SQL-транзакцией обеспечить нельзя: нужен outbox/reconciliation.
- Приёмка: send-success/INSERT-failure, потеря ответа send, рестарт между шагами.
  Намеренное создание второго сбора сохранять: повтор разрешён действующим
  контрактом `tests/collectionReliability.test.ts:303`. Дедупликация — по операции,
  а не по одинаковому содержимому разных действий пользователя.

### 11. P2 — изменение времени затирает свежий вид регистрации

- Место: `src/features/capture/captureManager.ts:208–303,369–397`,
  `src/features/capture/captureInteractions.ts:284–310`.
- Time edit отправляет snapshot вне общей очереди refreshCapture. Join или
  другое изменение времени могут завершиться раньше, затем старый edit затрёт
  их отображение. Ошибки fetch/edit проглатываются, UI получает успех.
- Исправление: все edits одной регистрации пропускать через одну очередь по ID;
  payload строить из последней committed записи, учитывать revision/dirty flag.
  Ошибки доставки отделить от сохранения данных, сообщать pending и повторять.
- Приёмка: управляемые interleavings join/time/time, отказ Discord, рестарт;
  финальный payload соответствует последней БД, ошибку доставки видно.

### 12. P2 — сетевой запрос удерживает SQL-транзакцию закрытия сбора

- Место: `src/services/captureExpiry.ts:26–55`.
- После SELECT FOR UPDATE выполняются fetch канала, fetch сообщения и edit.
  Discord rate limit/зависание удерживает соединение и row lock, задерживая
  нажатия на этот сбор. Последовательный worker задерживает и следующие сборы.
- Исправление: короткая транзакция фиксирует желаемое закрытие/версию и задание
  обновления; сеть — после commit через общую очередь из задачи 11. Для переноса
  времени сохранять проверку версии и вычисление актуального состояния.
- Приёмка: медленный Discord не удерживает соединение и не блокирует БД;
  перенос времени одновременно с закрытием даёт правильные кнопки.

### 13. P2 — сообщение в архиве запускает полную сетевую пересборку

- Место: `src/features/archive/updateLists.ts:43–45,71–79`,
  `archiveUnansweredList.ts:38–42`, `src/events/messageCreate.ts:45`.
- Обновление читает архивы/участников, последние сообщения веток и историю
  канала списков. Coalescing есть, но постоянный поток поддерживает повторные
  полные обходы. Префиксная команда в архиве ждёт updateLists до dispatch.
- Исправление: инвалидировать конкретную ветку, debounce с максимальной задержкой,
  registry IDs, ограниченный concurrency, периодическая полная reconciliation.
  Dispatch команды не должен ждать несвязанной пересборки; её ошибки обработать.
- Приёмка: burst из 100 событий даёт ограниченное число refresh; задержка ответа
  команды не зависит от размера архивного канала.

### 14. P2 — сохранение навигации обходит всю историю

- Место: `src/dashboard/navigationMessages.ts:48–79`,
  `src/dashboard/routes.ts:203,251,286`.
- Каждый sync заново читает архивы и историю каналов, пишет tracking в цикле;
  fetchAll:true сочетается с ручной пагинацией. Работа ожидается прямо в HTTP.
- Исправление: однократный ограниченный backfill с сохранённым курсором; затем
  только tracked IDs. Длительные синхронизации — durable jobs с прогрессом,
  дедупликацией по revision и retry; сохранение настроек не ждать всего обхода.
- Приёмка: второй sync не читает старую историю; рестарт продолжает backfill;
  HTTP быстро возвращает operation ID, ошибка задачи видна пользователю.

### 15. P2 — неполный поиск старых и private-архивов

- Место: `src/features/archive/archivesList.ts:53–56,78`.
- fetchArchived читает только первые 100, private-ветки не включены; архив
  существующего участника может отсутствовать в списке.
- Исправление: общий paginated snapshot обеих категорий, переиспользовать

  вместо линейного find по всем каналам для каждого участника.
- Приёмка: 101+ архивов и private-архив за первой страницей находятся корректно.

### 16. P2 — длинные списки ломают публикацию

- Место: `src/features/archive/archiveUnansweredList.ts:98–114`,
  `src/features/capture/captureManager.ts:149`.
- Неотвеченные и leftPlayers собираются без ограничения в один TextDisplay.
  При росте списка payload превышает лимит; данные уже могут быть сохранены,
  но публичное сообщение останется старым.
- Исправление: общая разбивка с учётом полного бюджета контейнера, компонентов
  и итогового текста; пагинация/сводка с доступом к полной истории.
- Приёмка: границы лимитов, длинные ники, несколько сотен записей; ни один
  участник не теряется и payload проходит ту же проверку, что при отправке.

### 17. P2 — парсер нормализует ошибочный ввод в другое время

- Место: `src/utils/dateUtils.ts:36–44`.
- Локально подтверждено: `32.01.2027 12:00` → 1 февраля,

- Приёмка: 31 апреля, високосный год, 24:00, 12:60, границы МСК-суток.

## Интеграции, очередь и БД

### 18. P2 — Telegram capture теряется после временной ошибки

- Место: `src/events/telegramCaptures.ts:84–90,124–130`.
- Событие отмечается обработанным до доставки; fetch/send failure подавляет его
  на 5 минут без автоматического retry. Успешный send + неуспешный track оставит
  объявление без автоматических результатов.
- Исправление: inbox/outbox по Telegram message ID, состояния delivery/tracking,
  Discord message ID, повторные попытки и восстановление незавершённых шагов.
- Приёмка: сбой send, сбой track и рестарт после успешной отправки; восстановление
  без необоснованного повторного объявления.

### 19. P2 — прямые Telegram-уведомления без deadline/retry

- Место: `src/events/telegramNotifications.ts:19–33`.
- Fetch без AbortSignal; каждое событие отправляется независимо. Всплеск не
  учитывает 429, сбой теряет уведомление, зависшие запросы накапливаются.
- Исправление: общий delivery worker/outbox, deadline, bounded concurrency,
  retry-after и backoff/jitter. Определить политику возможных дублей после
  неопределённого результата Telegram API.
- Приёмка: hung fetch, 429, 5xx, burst; очередь ограничена и наблюдаема.

### 20. P2 — неограниченная очередь ошибок

- Место: `src/services/telegramErrorReporter.ts:10,17–37`.
- Каждая console.error замыкает полный format(args) в цепочке Promise.
  Доставка последовательная, до 10 секунд на кусок; нет предела длины очереди
  и события. Error storm растит память, flush тормозит shutdown.
- Исправление: bounded buffer, лимит размера события, дедупликация и счётчик
  повторов, агрегация, backoff/429, deadline flush. Локальные логи сохранять
  независимо от Telegram. Редактирование секретов должно учитывать все реальные
  имена credentials, включая SUPABASE_URL, и структурированные поля ошибок.
  Факт утечки конкретного секрета этим аудитом не установлен.
- Приёмка: 10 000 ошибок при зависшей сети — ограниченные память/очередь;
  секреты из тестового env не попадают в отправленный текст.

### 21. P2 — три Discord REST-вызова на каждый API-запрос

- Место: `src/dashboard/auth.ts:37–43,114`.

## Как разделить модули

Это целевая схема постепенного извлечения существующего кода, а не требование
сразу создать все перечисленные файлы. Дополнительные процессы, Redis или
микросервисы не нужны без измеренной причины; имеющегося PostgreSQL достаточно
для durable jobs/outbox и блокировок.

| Сейчас | Предлагаемая граница | Инвариант |
|---|---|---|
| index.ts + ready.ts + побочные эффекты database.ts | bootstrap, lifecycle, HTTP app factory, миграции отдельно от pool | Импорт модуля не запускает сеть/DDL; каждый сервис имеет start/stop/status |
| dashboard/routes.ts | routes/config, templates, variables, publications, archives, majestic; общий auth/error middleware | Авторизация, guild scope, CSRF и аудит остаются обязательными для каждого маршрута |
| dashboard/store.ts | repository/revision, template catalog, settings definitions, migrations, audit | Одна точка транзакционной записи; чтения и версии имеют явный контракт |
| captureManager.ts | repository, registration transitions, message renderer, message update worker, creation operation | State transitions проверяются без Discord; один владелец публикации сообщения |
| invite handlers | application service + repository + Discord delivery | Accept/reject/create используют общую state machine и версии |
| archive builders/updateLists | thread snapshot/index, list renderers, managed message registry, refresh coordinator | Нет удаления по одному author ID; полные обходы вынесены из event hot path |
| Telegram send paths | delivery queue/outbox, transport, subscription/inbox handlers | Общие timeout/retry/429/limits, отдельная политика надёжности каждого типа события |
| frontend/App.tsx | session shell, resource cache, mutation status, draft registry, page controllers | UI-страница не владеет единственным экземпляром несохранённых данных |
| shared/public formatting | общие payload limits/schema и чистые функции рендера | UI и API проверяют тот же финальный документ, что отправляется в Discord |

Порядок извлечения: зафиксировать тестом текущее поведение → перенести одну
границу без изменения поведения → прогнать тот же тест → отдельно исправлять
дефект. Ускорение получается от сокращения I/O, сериализации, DOM и очередей;
модули помогают сделать эти ограничения явными и проверяемыми.

Существующий runtimeDiagnostics уже измеряет event loop, RSS и состояние pool;

Предлагаемые acceptance-сценарии, не результаты уже выполненной нагрузки:

1. 50 конкурентных join/leave одного сбора: состав/ёмкость корректны, ACK

5. Очередь Telegram 10k jobs, 429/5xx, restart, при необходимости два worker:

7. Кратковременный отказ БД, SIGTERM на каждом шаге операции, повторный запуск:
