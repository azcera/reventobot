# План миграции Revento на TypeScript и повышения устойчивости

Дата: 11 ноября 2026 года.

## 1. Результат и границы

Цель — типизировать сервер, дашборд, общие модули, служебные скрипты и тесты; сохранить существующие сценарии и данные; сократить лишние обращения к Discord; обеспечить своевременное подтверждение взаимодействий и корректную конкурентную обработку.

Этот документ — план по результатам просмотра кода. Изменения приложения и удаление файлов ещё не выполнялись. Перенос расширений сам по себе не исправит тайм-ауты, гонки и ошибки внешних сервисов.

Базовое допущение: один процесс бота, один Discord-сервер примерно на 200 участников и существующая PostgreSQL. Начать без Redis, микросервисов и шардирования. Если фактический запуск использует несколько экземпляров, до реализации очередей потребуется межпроцессная координация.

## 2. Что установлено по коду

| Участок | Наблюдение | Что требуется |
| --- | --- | --- |
| `src/events/interactionCreate.js` | Общий `try/catch` охватывает исполнение команд, но не все ветки кнопок, меню и форм. Неизвестная команда может завершиться без ответа | Единая граница ошибок, явные маршруты и ответ для неподдерживаемых/устаревших действий |
| `src/features/invite/inviteApplication.js`, `inviteModeration.js`, `inviteModalHandler.js` | Есть `deferReply(...).catch(() => {})`, после которого обработка продолжается | При неуспешном подтверждении прекращать изменения; различать просрочку, повторный ответ и сетевую неопределённость |
| `src/features/capture/captureManager.js` | Запись/выход уже подтверждаются через `deferUpdate`; используются транзакции и `FOR UPDATE`. При этом `editReply` ожидается до `COMMIT` | Сохранить защиту состояния, вынести сетевую публикацию за пределы транзакции, обеспечить порядок и восстановление публикаций |
| `src/events/mclLists.js`, `src/services/mclLists.js` | События изменения ролей ставят полную синхронизацию в последовательную очередь. Каждый проход с настроенными списками вызывает `guild.members.fetch()` и редактирует сообщения; одинаковые задания не объединяются | Объединять обновления, загружать состав совместно, обновлять только затронутые списки и изменившееся содержимое |
| `src/services/discordMembers.js` | Уже есть совместное ожидание одной загрузки, кэш на 30 секунд и ограниченные повторы Gateway-запроса состава | Переиспользовать и проверить инвалидирование; не создавать второй аналогичный сервис |
| `src/features/archive/updateLists.js` | Читает последние 20 сообщений, затем редактирует/удаляет их по позиции, исключая сообщения проверки членства | Хранить идентификаторы собственных сообщений, проверять владельца, объединять обновления, сравнивать содержимое |
| `src/events/onThreadCreate.js`, `onThreadDelete.js`, `onMessageDelete.js` | Вызывают обновление архивных списков по событиям | Проверить фильтры событий и исключить циклы обновлений, объединять всплески событий |
| `src/services/rolePrefixSync.js` | Уже пропускает неизменившиеся и недоступные ники, обрабатывает участников последовательно | Сохранить полезные проверки, согласовать записи с другими источниками изменения ников |
| `src/services/majesticNicknameScheduler.js` | Следующий запуск планируется после завершения текущего | Сохранить существующую защиту от наложения запусков |
| `index.js`, `src/utils/loadCommands.js` | Динамическая загрузка `.js`, пути через `__dirname`, статика, запуск и HTTP-маршруты в одной точке | При компиляции явно учесть пути сборки, ресурсы и загрузку команд/событий |
| `public/*.js` | Общие исходные модули используются браузером и сервером | Переносить с сохранением обоих потребителей; не удалять как старый фронтенд |
| `src/services/database.js` | Инициализация схемы импортирует `FAMILY_WAR_SCHEMA` из `familyWars`, хотя запуск API-сервиса отключён | Отключённость функции не доказывает, что файл можно удалить |

Это риски и точки изменения, а не доказательство причины каждого случая «Бот не отвечает». Для установления причин нужны длительности обработчиков, подтверждений и очередей в рабочем окружении без записи токенов и персонального содержимого.

## 3. Приоритеты и этапы

### Этап 0. Зафиксировать исходное поведение

1. Установить зависимости из lockfile через `npm ci` в среде разработки. Зафиксировать поддерживаемую версию Node и способ развёртывания.
2. Выполнить существующие `npm test`, `npm run build`, `npm run test:dashboard`; отделить проблемы окружения от дефектов приложения.
3. Составить матрицу сценариев: команды, кнопки, меню, формы, заявки, капты/группы, архивы, MCL, расписания, Telegram, Majestic, редактор и публикация из дашборда.
4. Для каждого взаимодействия указать маршрут, доступ, первый ответ, побочные эффекты и ожидаемую реакцию при повторном нажатии.
5. Добавить измерения: время до отправки и успешного подтверждения первого ответа, общее время обработки, ожидание очереди и БД, задержка event loop, ошибки Discord и размеры очередей. Привязывать записи к interaction ID и операции; исключить токены, сессии и тексты заявок.

Готовность: понятны исходные проверки и список сценариев; есть способ измерять улучшение. При первоначальном просмотре `git status --short` был пуст. Пробный `npm test` завершился с ошибками `MODULE_NOT_FOUND`, включая `discord.js`: успешный исходный прогон пока не получен.

### Этап 1. Своевременный ответ Discord — первый рабочий приоритет

1. Ввести типизированный реестр обработчиков с явной стратегией первого ответа: обычный ответ, отложенный личный ответ, подтверждение обновления сообщения или открытие формы.
2. Подтверждать обычные длительные действия до ожидания БД, внешних API и очередей. Для `showModal` быстро проверить доступ и открыть форму первым ответом: нельзя автоматически делать `deferReply` перед каждой кнопкой.
3. Назначить одного владельца первого ответа. Не применять таймер с безусловным `defer`, который может столкнуться с `reply` или `showModal`. Состояния `replied/deferred` — часть защиты, но сами по себе не заменяют координацию параллельных ответов.
4. Покрыть единой обработкой ошибок весь путь маршрутизации, включая проверки доступа. После defer завершать исходный ответ через `editReply`; `followUp` использовать для отдельного уведомления по смыслу сценария.
5. После ошибки подтверждения не продолжать бизнес-изменения вслепую и не повторять первый ответ бесконечно. Записывать причину и состояние; отдельно обрабатывать неоднозначный сетевой результат.
6. Для старой кнопки, удалённой сущности, отключённой функции и отсутствия прав давать понятный ответ. Прекратить молчаливые выходы там, где взаимодействие предназначено этому боту.
7. Ввести ограничение повторного запуска по сущности/операции. Сохранять порядок действий пользователя: «войти → выйти» нельзя ошибочно схлопнуть в одно действие. Повторную доставку того же interaction ID можно дедуплицировать.

Готовность: каждый поддерживаемый маршрут имеет явный первый ответ и проверку ошибок; медленная БД или Majestic не задерживают его отправку. Контрольные тесты покрывают также формы и двойные нажатия.

### Этап 2. Сократить Discord-запросы и разнести конкурирующие операции

1. Сохранить встроенное управление REST-лимитами discord.js. Не заменять его фиксированной общей задержкой и не пытаться обходить лимиты.
2. Разделить подтверждения взаимодействий и фоновые задания: первый ответ никогда не ждёт прикладной очереди синхронизации. Фоновые операции получают ограниченную конкурентность и ограниченную длину очереди; разные сущности не блокируют друг друга без причины.
3. Для записи сообщения использовать очередь по message ID: объединять запросы на перерисовку, сериализовать публикации, брать последнюю версию данных. После начального короткого окна объединения не откладывать обновление бесконечно при непрерывных событиях.
4. Для каптов сначала атомарно сохранять состояние и версию в PostgreSQL, затем публиковать представление. Не держать транзакцию открытой во время Discord-запроса. Сохранить информацию о требуемой публикации в той же транзакции, чтобы перезапуск не потерял обновление; повторная публикация должна быть безопасной. Перед очередной публикацией перечитывать актуальную версию, не допускать окончательного перезаписывания свежего состояния старым.
5. MCL и архивы: объединять события в один проход с признаком повторного обновления, если изменения пришли во время выполнения. Не накапливать по полной синхронизации на каждое событие. Не отправлять одинаковый payload повторно.
6. Переиспользовать `loadDiscordMembers` для массовых чтений. Точечные изменения ролей и проверки доступа при необходимости выполнять по свежему участнику; не подменять критичные проверки устаревшим кэшем. После reconnect и неполных событий предусмотреть повторную загрузку.
7. Координировать запись ников по member ID между Majestic, префиксами и `guildMemberUpdate`: определить единое правило формирования итогового ника и пропускать совпадения. Не выполнять конкурирующие полные перезаписи набора ролей.
8. Тайм-ауты и ограниченные повторы применять по типу операции. Учитывать встроенные повторы библиотеки, не повторять постоянные 403/404, не дублировать создание сообщений/каналов при неоднозначном результате сети. Для внешних интеграций использовать увеличивающуюся задержку и случайный разброс.
9. При недоступности интеграции возвращать контролируемый результат и приостанавливать соответствующую работу; бот и дашборд продолжают обслуживать независимые сценарии.

Готовность: всплеск событий не вызывает столько же полных загрузок состава/редактирований; очереди ограничены, обновления не теряются, после сбоя Discord представление сходится с БД.

### Этап 3. Инфраструктура TypeScript и общие контракты

1. Добавить TypeScript и необходимые пакеты типов как зависимости разработки. Сначала сохранить CommonJS сервера; фронтенд оставить с ES modules и Vite. Не совмещать миграцию типов с полной сменой модульной системы.
2. Разделить настройки компилятора для сервера, браузера и тестов/скриптов. Для TypeScript включить `strict`, `noImplicitAny`, `useUnknownInCatchVariables`; отдельно включать и устранять ошибки `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`.
3. Во время перехода допустить оставшиеся JS-модули, отслеживая их список. Не считать завершением миграции наличие `allowJs`, массовых `any`, `@ts-ignore` или приведения всего JSON через `as`.
4. Типизировать контекст приложения и расширения Discord-клиента, команды разных видов, маршруты взаимодействий, жизненный цикл сервисов, настройки, шаблоны, результаты БД, планы синхронизации и ошибки.
5. Создать общие контракты HTTP-запросов/ответов и данных шаблонов. Внешние данные принимать как `unknown` и проверять во время выполнения: JSON, переменные окружения, сохранённые настройки, строки БД и ответы интеграций. TypeScript не проверяет их автоматически.
6. Добавить команду проверки типов; сервер компилировать в отдельный каталог сборки. Явно копировать необходимые JSON/изображения и сохранить пути к статике. Исключить загрузку одновременно исходных и скомпилированных событий.
7. Согласовать сборку общих браузерных модулей: исходники на TypeScript, JS на выходе для существующих URL. Сохранить работоспособность серверных импортов, прокси Vite и браузерных фикстур.

Готовность: проверка типов проходит для перенесённого кода, сборка запускается на фикстурах без подключения к рабочему Discord и PostgreSQL; ресурсы и пути не потеряны.

### Этап 4. Переносить модули последовательно

Порядок: чистые функции и контракты → инфраструктура ответов/очередей → капты и заявки → архивы/MCL/расписания → Majestic/Telegram → API/настройки/публикация → React → скрипты и тесты.

Для каждого модуля: сохранить поведение тестом, перенести `.js/.jsx/.mjs` в `.ts/.tsx`, типизировать границы, обновить непосредственных потребителей, выполнить ближайшие проверки. Не переносить весь проект одной непроверяемой правкой.

На фронтенде типизировать props, состояние редактора, формы, ответы API, ошибки, сохранённые черновики и ссылки на DOM. Проверить отмену/игнорирование устаревших ответов и защиту от повторной отправки форм. Авторитетные права и валидация остаются на сервере.

Готовность: весь поддерживаемый собственный исполняемый исходный код и тесты типизированы; оставшиеся JS-файлы — только явно описанные артефакты сборки или необходимые минимальные конфигурационные адаптеры. CSS, HTML и JSON остаются в своих форматах.

### Этап 5. Упорядочить архитектуру и удалить подтверждённо лишнее

Целевая схема — существующий модульный монолит:

- команды, события и HTTP-маршруты принимают ввод, проверяют доступ и вызывают сценарий;
- сценарии заявок, каптов, архивов и интеграций содержат бизнес-правила;
- инфраструктура выполняет Discord-запросы, запросы БД, публикацию и фоновые задания;
- общие чистые типы и функции используются сервером и интерфейсом, не импортируя Discord-клиент или секретные настройки в браузер.

Не создавать универсальный фреймворк обработчиков и репозитории для каждой таблицы без практической необходимости. `index` оставить точкой сборки зависимостей и управления запуском/остановкой; маршруты дашборда разделять по функциям в ходе их переноса.

Очистка выполняется по доказательствам:

1. Для каждого кандидата проверить импорты, динамические загрузчики, регистрацию событий/команд, ссылки из HTML, скриптов, документации и схемы БД.
2. Не объявлять `testcapt`, отключённый Family Wars или файл с необычным названием мусором без проверки назначения. Удаление рабочей функции требует подтверждения её ненужности; перенос не должен скрыто уменьшать функциональность.
3. Удалять старые реализации после переключения всех потребителей. Объединять дубли по одинаковым правилам и контрактам, сохраняя различия сценариев.
4. Старые тесты сохранять, если они проверяют актуальное поведение. Заменять проверки внутреннего устройства поведенческими перед удалением; возраст теста не является основанием для удаления.
5. Генерируемые каталоги и локальные отчёты отличать от исходников. Не удалять данные, настройки, ресурсы и историю миграций БД. Зависимости удалять только после проверки использования.
6. Обновить соответствующие разделы README и карту AGENTS.md после изменения путей и команд.

Готовность: список удалённых файлов с обоснованиями, сохранённые сценарии, отсутствие параллельных старых реализаций и потерянных обработчиков.

### Этап 6. Проверка нагрузки и ввод в эксплуатацию

Проверять на моках Discord и БД/тестовой БД, с управляемыми задержками и ошибками. Моки не доказывают реальную сетевую скорость Discord, поэтому после локальной проверки нужен ограниченный прогон на отдельном тестовом сервере.

| Сценарий | Критерий |
| --- | --- |
| 20 и 50 одновременных взаимодействий; отдельно всплеск 200 для проверки запаса | В контролируемом тесте каждый допустимый запрос получает ровно одно первоначальное подтверждение, без необработанных исключений |
| Медленная БД/интеграция, включая задержку более 3 секунд | Первоначальный ответ отправлен до медленной работы; итог — результат или контролируемая ошибка |
| 50 пользователей записываются на один капт | Нет дублей, потерянных записей и переполнения основного состава; итоговое сообщение соответствует БД |
| Повторные нажатия, запись и выход, принятие и отклонение заявки разными модераторами | Предсказуемый порядок/конфликт, одна допустимая бизнес-операция, повтор не создаёт второй канал или заявку |
| 100 событий изменения ролей | Нет 100 полных загрузок состава и одинаковых перерисовок; после завершения проходов списки актуальны |
| 429, 403, 404, сетевой тайм-аут и восстановление | Ограниченные повторы только допустимых операций, нет шторма запросов и бесконечной очереди |
| Перезапуск между сохранением БД и публикацией | Неопубликованное состояние восстанавливается; новые сообщения не дублируются |
| Формы и устаревшие компоненты | Формы открываются корректным первым ответом, устаревшие действия объясняются пользователю |
| Дашборд на desktop/mobile | Сохраняются вход, CSRF, доступ, конфликты ревизий, черновики и публикация |

Целевой внутренний бюджет: начать первоначальный ответ сразу после быстрой маршрутизации, стремиться к p99 успешного подтверждения менее 1 секунды в контролируемой нагрузке; отдельно фиксировать случаи приближения к 2 секундам и все превышения 3 секунд. Для результатов фоновых действий измерять отдельные показатели. Число участников сервера само по себе не задаёт число одновременных действий.

Перед выпуском: проверка типов, серверные тесты, сборка фронтенда, Playwright, тесты конкуренции и восстановления. Затем тестовый сервер, резервная копия данных, развёртывание одной версии процесса, наблюдение за метриками. Откат должен учитывать совместимость схемы и формата данных; старый и новый бот одновременно под одним токеном не запускать.

## 4. Рекомендуемый порядок отдельных изменений

1. Исходные проверки, матрица взаимодействий и измерения.
2. Быстрое подтверждение, формы, единая обработка ошибок и неизвестных действий.
3. Транзакции каптов, порядок публикаций и восстановление после сбоев.
4. Объединение обновлений MCL/архивов, общий кэш участников и координация ников.
5. Конфигурация TypeScript и общие контракты; далее небольшие изменения по модулям из этапа 4.
6. Подтверждённая очистка, финальная проверка нагрузки и инструкции развёртывания.

Срочные исправления устойчивости допустимо делать до полной миграции. Полное принятие работ — после всех этапов, а не после первого успешного `tsc`.

## 5. Ограничения гарантий

Можно устранить внутренние причины пропуска подтверждений и проверить конкурентные сценарии. Нельзя гарантировать отсутствие сообщения «Бот не отвечает» при недоступности Discord, обрыве сети или остановленном процессе. TypeScript снижает число ошибок данных и контрактов, но не заменяет обработку сбоев, ограничение очередей и наблюдение.

## 6. Официальные источники

- [Discord: получение взаимодействий и ответы](https://github.com/discord/discord-api-docs/blob/main/developers/interactions/receiving-and-responding.mdx): первоначальный ответ в течение 3 секунд; токен для дальнейшей работы действует 15 минут; тип ответа выбирается по сценарию.
- [Discord: ограничения частоты запросов](https://github.com/discord/discord-api-docs/blob/main/developers/topics/rate-limits.mdx): учитывать ограничения маршрутов и ответы сервера, не зашивать один предел для всех операций.
- [discord.js: реализация REST](https://github.com/discordjs/discord.js/blob/main/packages/rest/src/lib/REST.ts): библиотека уже управляет обработчиками ограничений запросов. Перед настройкой реализации сверить API с фактически установленной версией из lockfile.
